The system property `archispark_image` (`GET /api/property-definitions`,
`is_system: true`) sets the icon shown for an element: on its node in the
ReactFlow canvas, next to its name in the element edition page, and in
server-rendered SVG view exports. Setting it on an element overrides the
element's **default ArchiMate type icon** — see
[Default ArchiMate icons](#default-archimate-icons) — with an icon picked
from ArchiSpark's **image library**: a draw.io-style collection of icon
**packs**. Its value is the picked item's **slug**, not an arbitrary URL.

## Default ArchiMate icons

Every ArchiMate 3.1 element type has a default icon shown on its node
whether or not `archispark_image` is set — these are not a pack: they're TSX
components compiled into `@workspace/image-library` and rendered directly by
the ReactFlow canvas, with zero database lookup. One icon file per type,
stored in `packages/image-library/assets/archimate/{ArchimateType}.svg` and
compiled via `pnpm --filter server gen:icon-pack`
(`apps/server/scripts/generate-archimate-icon-pack.ts`) into
`packages/image-library/src/archimate-icons/` — grouped below by layer. This
is unrelated to the corner glyph ArchiSpark's SVG renderer draws on each
element shape in exported views (`lib/archimate/archimate-icons.ts`); the
two are generated and maintained independently.

To change a default icon: edit its source SVG under
`packages/image-library/assets/archimate/`, then run
`pnpm --filter server gen:icon-pack` and commit the regenerated `.tsx`
files — no migration, no deployment step beyond the usual build.

## Packs

Packs are instance-wide, not organization-scoped — every organization sees
the same list, managed by `platform_admin` from `/platform/image-library`
and `/platform/plugins`. A pack is either:

- **System** — read-only, seeded once from the vendor icon sets (see
  [System packs](#system-packs)).
- **Custom** — created and populated by a `platform_admin`, either one item
  at a time from `/platform/image-library` (or the
  `POST /api/image-library/packs/:packId/items` API — stored in Vercel
  Blob), or in bulk from `/platform/plugins` (or the
  `POST /api/image-library/packs/:packId/install` API — stored inline in
  Postgres, see [Plugin packs](#plugin-packs)). See
  [API reference](/docs/developer-guide/reference/api-reference#image-library).

Setting `archispark_image` on an element stores a pack item's **slug** —
pick it from the image picker on the property's value in the element
edition page. Resolution is scoped to the workspace's organization: an item
from one of the organization's own custom packs is preferred over a system
item sharing the same slug, so a custom pack can override a vendor icon by
reusing its slug; a slug must be unique among system-pack items, and unique
per organization among that organization's own pack items — enforced by two
partial unique indexes on `image_pack_items`, not by application code.
Values written before the image library existed (an HTTP(S) URL or a
relative path) keep working as a legacy fallback.

### Updating a system pack

Editing an already-seeded vendor pack's icons requires two steps: regenerate
the assets and write an incremental migration, then apply that migration to
the database.

1. Edit the source SVGs under
   `packages/image-library/assets/<aws|azure|gcp>/*.svg` (only reachable by
   re-running `pnpm --filter server gen:cloud-icon-packs -- --source <dir>` against an
   updated vendor source directory — see the script's header comment).
2. Run `pnpm --filter server gen:cloud-icon-packs`. It diffs the new content
   against what's already committed and writes a new incremental migration
   (`{idx}_sync_<pack>_icon_pack_assets.sql`) only for the icons that
   actually changed — the original seed migration
   (`0027`/`0028`/`0029_image_pack_*.sql`) is never rewritten once it exists.
3. Commit the changed assets, the new migration, and the updated
   `packages/db/drizzle-pg/meta/_journal.json`.
4. Apply the migration to the target database with
   `pnpm --filter @workspace/db migrate:prod` — this is currently a
   **manual** step; committing the migration alone does not change what's
   served until it's applied.

## Plugin packs

A `platform_admin` can install a whole icon pack in one action from
`/platform/plugins` (or `POST /api/image-library/packs/:packId/install`),
without a code change or a deployment — the runtime counterpart to the
`generate-*-icon-pack.ts` scripts above, for icon sets that aren't shipped
with ArchiSpark itself.

- **Bundle**: one or more `.svg` files, plus an optional `manifest.json`
  naming the pack's `name`/`description` and, per item, an explicit
  `slug`/`name` keyed by file name. Without a manifest, each file's slug and
  name are derived from its filename.
- **Limits**: 1000 items per install, 512 KB per SVG file, 25 MB per bundle.
- **Storage**: items are inserted as `inline_svg` — the same storage kind as
  every system pack — not Vercel Blob. Only SVG is accepted for this path;
  raster formats (PNG/JPEG/WebP) still require the single-file upload flow
  at `/platform/image-library`, which stores in Blob.
- **Safety**: every SVG is rejected outright (not silently stripped) if it
  contains a `<script>`, `<foreignObject>`, an `on*` event handler
  attribute, or an `href`/`xlink:href` pointing outside the document (only
  `#fragment` and `data:image/...` are allowed) — see
  `apps/server/lib/archimate/svg-sanitize.ts`. The same check applies to the
  single-file upload flow.

Unlike `generate-archimate-icon-pack.ts`/`generate-cloud-icon-packs.ts`,
this path never touches `packages/image-library/assets/`, never writes a
Drizzle migration, and never produces a system pack (`is_system` stays
`false`) — it's a runtime-only, custom-pack mechanism.
